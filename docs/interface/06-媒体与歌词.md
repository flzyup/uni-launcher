## 2. 快照里的媒体 / 歌词键

> 快照整体结构、增量包（`partial`）合并规则见 [04-snapshot-schema](04-snapshot-schema.md) §4-§5；本节只展开歌词/媒体键的语义，且以源码为准。

`snapshot()` 返回 `JSONObject`（`MediaAdapter.java:361`），`controller != null` 分支（`:369-424`）。

### 2.2 时间 / 播放键（单位与哨兵）

| 键 | 类型 | 单位 | 哨兵 / 缺省 | 行号 |
| --- | --- | --- | --- | --- |
| `positionMs` | long | 毫秒 | 未知时为 `0`；`<0` 的原始位置也被归零 | `:417`；归一 `position()` `:478-484` |
| `positionKnown` | boolean | — | `p != null && p.getPosition() >= 0` | `:417` |
| `durationMs` | long | 毫秒 | `0` = 未知（`Math.max(0, …)`） | `:373`、`:416` |
| `sampledAtMs` | long | 墙钟毫秒（`System.currentTimeMillis()`） | — | `:412`、`:418` |
| `speed` | float | 播放倍速 | `p == null` 时写 `0` | `:419` |
| `playing` | boolean | — | `p != null && state == STATE_PLAYING` | `:390` |

`positionMs` 的语义是「采样那一刻的位置」，**已由原生按单调时钟补过**：`position()` 在 `STATE_PLAYING` 且 `lastPositionUpdateTime > 0` 时加上 `elapsedRealtime - lastPositionUpdateTime` 乘以 `speed`（`MediaAdapter.java:478-484`）。所以 Dart 端再推进时用的是 `sampledAtMs`（墙钟）而不是单调时钟，见 §2.4。

`speed == 0` 的两种情况：

- 原生 `LyricCast.State` 把 `<= 0` 归一成 `1f`（`LyricCast.java:43`），副屏不受影响；
- Dart `MediaTimeline.speed` 直接取快照值（缺键才用 `1`，`app/lib/model/lyrics.dart:66`），但 `at()` 先看 `playing`（`:70`），`p == null` 时 `playing` 必然为 false，`elapsed` 恒为 0，所以位置不会被冻住。

**待确认**：某些播放器 `PlaybackState.getPlaybackSpeed()` 在未设置时返回 `0` 还是 `1`，本仓库没有对该返回值做兜底判断。

### 2.3 无会话时的快照（`controller == null`）

`MediaAdapter.java:425-437`：只从 prefs `uni_last_track` 取回上次的 `source/title/artist/album/duration/position`，写 `cached=true`、`positionKnown=false`、`reason="播放器未连接，显示上次播放"`（`:436`）。

- **不写** `lyrics`/`lyricsSource`/`lyricTimeline*` 任何键（整个分支没有这些 put）。
- **不调用** `LyricCast.publish` —— 副屏保留上一帧（05 文档 §8 第 4 条）。

| 消费者 | 用哪些键 | 行号 |

## 3. 时间轴 JSON v1

### 3.1 结构（Java 生产者 + 两个解析器）

```json
{"v":1,"lines":[
  {"t":1000,"d":2000,"x":"你好世界","tr":"第一行","ro":"nihao shijie",
   "w":[[1000,500,"你"],[1500,500,"好"],[2000,1000,"世界"]]}
]}
```

| 键 | 类型 | 含义 | 是否可缺 |
| --- | --- | --- | --- |
| `v` | int | 版本，固定 `1` | 生产者总写（`LyricTimeline.java:668`） |
| `lines` | array | 行数组，按 `t` 升序 | 总写 |
| `t` | long | 行起始，毫秒 | 总写（`:646`） |
| `d` | long | 行时长，毫秒；`0` = 无行时长 | 总写（`:647`） |
| `x` | String | 行文本 | 总写（`:648`） |
| `tr` | String | 翻译 | 空时省略（`:649`） |
| `ro` | String | 罗马音/罗马字 | 空时省略（`:650`） |
| `w` | array | 词数组，每项 `[startMs, durationMs, text]` | 无词级时省略（`:651-661`） |

生产者：`LyricTimeline.toJson()`（`LyricTimeline.java:640-672`）。

解析器一（Java，磁盘缓存回填）：`LyricCatalog.fromJson(JSONObject)`（`LyricCatalog.java:589-612`）—— 读 `lines[].{t,d,x,tr,ro,w}`，`w` 项要求 `length >= 3`（`:602`），最后 `LyricTimeline.fromLines(...)` 按时间入 `TreeMap` 去重排序（`LyricTimeline.java:201-207`）。

解析器二（Dart）：`LyricTimeline.parse(Object? payload)`（`app/lib/model/lyric_timeline.dart:183-225`）带四道护栏：

| 护栏 | 值 | 行号 |
| --- | --- | --- |
| payload 必须是 String，长度上限 | `2_000_000` 字符 | `:184` |
| 行数上限 | `maxLines = 4000` | `:169`、`:197` |
| 单行文本上限 | `maxTextLength = 4096`（`trimRight` 后截断） | `:170`、`:375-381` |
| 丢弃条件 | `x` 空且 `w` 空 | `:212` |
| 排序 | 按 `timeMs` 升序 | `:223` |

### 3.2 行/游标常量（两侧对照）

| 常量 | Java | Dart |
| --- | --- | --- |
| 无行时长时的保持时长 | `PLAIN_LINE_HOLD_MS = 5000`（`LyricTimeline.java:39`），`Line.endMs()` `:99-102` | `LyricTimeline.holdMs = 5000`（`lyric_timeline.dart:167`），`LyricLine.endMs` `:43` |
| 间奏判定阈值 | `MIN_INTERLUDE_MS = 5000`（`:37`），`at()` `:507-519` | `minInterludeMs = 5000`（`:168`），`at()` `:253-275` |

| 相邻行窗口 | ±3 行（`:612-631`） | ±3 行（`:351-371`） |

### 3.3 `sungPrefix()`：两侧规则与位置

| 侧 | 位置 | 规则 |
| --- | --- | --- |
| Java | `LyricTimeline.Cursor.sungPrefix()` `LyricTimeline.java:158-167` | ① `!wordTimed` → `""`；② `currentWord` 空 → `completed`；③ `trailingWord` → `completed + currentWord`；④ 否则按 `permille` 向上取整算「已唱码点数」`(permille*count+999)/1000`，再按**码点**取前缀（`:169-174` `takeCodePoints`，用 `offsetByCodePoints`） |
| Dart | `LyricCursor.sungPrefix` → `_songPrefix` `lyric_timeline.dart:123`、`:142-154` | 同上四条，取整公式 `(permille * count + 999) ~/ 1000`，取前缀用 `runes`（`:156-163`） |

`trailingWord` 的判定两侧不是同一份实现（结论相同、判据细节不同）：

| 侧 | 位置 | 判据 |
| --- | --- | --- |
| Java | `isTrailing` `LyricTimeline.java:577-585` + `onlyPunctuation` `:587-610` | `durationMs < 1000` 或当前词是纯标点 → false；否则看后续第一个非空词是否纯标点 |
| Dart | `_isTrailing` `lyric_timeline.dart:331-339` + `_onlyPunctuation` `:341-349` | `durationMs < 1000` 或当前词纯标点 → false；后续第一个非空词是否纯标点（正则 `[\s\p{P}\p{S}]`） |

Java 用 `Character.getType` 的白名单（破折号/括号/引号/连接符/数学·货币·修饰·其他符号，`:596-606`），Dart 用 `\p{P}\p{S}`，**理论上存在边缘字形差异**（例如 Java 未把 `OTHER_NUMBER` 算作标点，Dart 也不把 `\p{N}` 列入）—— 当前两侧都是「标点 ∪ 符号」，行为一致；若以后有人改其中一侧，必须先跑 `LyricCastTest.theSungPrefixIsSharedWithTheFlutterSide`（`:53-63`）。

Dart 独有三样（Java `Cursor` 没有）：

| 成员 | 语义 | 行号 |
| --- | --- | --- |
| `elapsedMs` | 行内已过毫秒，无行时 `-1` | `:94`、`:323` |
| `estimatedSungPrefix` | 纯 LRC 的**可选**均分估算（必须显式开 `estimatedKaraoke`） | `:126-132`；开关 `lyric_karaoke.dart:110`、`:181` |
| `lineProgress01` | 行内进度 `0..1`，未知 `-1` | `:135-138` |

## 4. 编码支持表（`LyricCodecs` → 增强型 LRC）

`LyricCodecs` 的职责：把各家的私有容器统一压成「增强型 LRC body」`[lineStart,lineDur](wordStart,wordDur,0)word…`，再交给 `LyricTimeline.parseEnhanced` / `LyricTimeline.parse(…, yrc, …)`（类注释 `LyricCodecs.java:16-33`）。

**统一出口**：`LyricTimeline.parseEnhanced(String)`（`LyricTimeline.java:237-239`）= `parse("", "", enhanced, "")`。

| 格式 | 入口方法 | 容器 / 密钥 | 词标记位置 | 时间基准 | 关键行号 |
| --- | --- | --- | --- | --- | --- |
| **LRC（行级）** | `LyricTimeline.parse(lrc, tr, yrc, romaji)` `:217-234` → `timedLines` `:255-274` | 纯文本；`[mm:ss.xx]` 或 `[mm:ss:xx]`；支持 `[offset:±ms]` | 标记在**行首** | 绝对毫秒 | `TIME_TAG` `:45-46`；`offsetOf` `:241-253`；小数位归一 `toMillis` `:359-367` |
| **增强型 LRC / YRC** | `LyricTimeline.parse(…yrc…)` `:276-313` | 纯文本；`[start,dur](wordStart,dur,0)text` | 标记在**词前**（标记之间的文本归属**后一个**标记） | 绝对毫秒 | `YRC_LINE` `:47`、`YRC_WORD` `:48`；词级优先于行级 `:222-225` |
| **KRC（酷狗）** | `LyricCodecs.kugou(String base64)` `:68-84` → `krcToEnhanced` `:93-108` | base64 → 跳过前 4 字节头 → XOR `KRC_KEY`（16 字节，`:38-41`）→ zlib inflate（上限 `MAX_INFLATED = 10MB`，`:35`） | 标记在**词前**：`<start,dur,0>text` | 词偏移**相对行首**，输出时加 `lineStart`（`wordsToEnhanced(..., absolute=true)` `:102`、`:439-461`） | `KRC_LINE` `:47`、`KRC_WORD` `:48`；语言标签 `kugouLanguage` `:87-91`；翻译 `kugouTranslation` `:114-151` |
| **QRC（QQ 音乐）** | `LyricCodecs.qq(String payload)` `:156-174` → `qrcToEnhanced` `:176-198` | `hex → 3DES(ECB) → zlib`；密钥 `QRC_KEY = "!@#)(*$%123ZXC!@!@#)(NHL"`（24 字节，`:43`）；先试 `DESede/ECB/PKCS5Padding`，失败退 `NoPadding`（`:509-518`）；解密后从 `LyricContent="…"` 里取正文（`:51-52`） | 标记在**词后**：`text(start,dur)` | 绝对毫秒 | `QRC_WORD` `:50`；XML/CDATA 提取 `cdata` `:485-488`；实体还原 `entities` `:201-206` |

| **MRC（咪咕）** | `LyricCodecs.migu(String hex)` `:261-305` → `miguToEnhanced` `:311-342` | 每 16 个 hex 字符一块 → XXTEA 形状的分组解密（`delta = 2654435769`，`:276`；9 个 `long` 密钥，`:277-281`）→ UTF-16LE | 标记在**词后**：`text(start,dur)` | 绝对毫秒 | `MRC_LINE` `:53`、`MRC_WORD` `:54`；`mix` `:307-309` |

| **增强型 → 行级** | `LyricCodecs.enhancedToPlain(String)` `:371-383` | 去掉 `(s,d,x)` 标记，回写 `[mm:ss.mmm]` | — | — | 供 QQ 只有词级时给翻译对齐用（`LyricCatalog.java:376`） |

**「标记在前还是在后」的实现差异**（这是最容易写出错的一行代码）：

- 在前（KRC、YRC）：`wordsToEnhanced` 用 `body.substring(previousEnd, word.start())` 把两标记之间的文本配给**后一个**标记（`LyricCodecs.java:446-459`）；`LyricTimeline.wordTimedLines` 同构（`:292-302`）。
- 在后（QRC、Kuwo、MRC、AWLRC）：正则是 `(text)(marker)`（QRC `:50`）或切片器 `textBeforeMarkers` 累积 `pending` 文本再配给当前标记（`:409-427`）。

**`LyricCodecs.migu` 已接线**（2026-11）：`LyricCatalog.miguLyric` 用 `mrcText` + `miguToEnhanced` 解 `mrcUrl` 的词级文档，空则退回行级 `lrcUrl`。同时修掉三处真实缺陷：MRC 字段分隔符不是纯 `\n`（`\r\n` 混 `\u2028`、文件头带 `[ti:]`/`[ar:]`，按行切会把整份文档判成「无词标记」）；词标记其实跟在音节**后面**（按「在前」解析会丢每行首字）；`resourceinfo.do` 只认 `contentId`（`copyrightId` 返回空 `resource`）。细节见 [LYRIC_PIPELINE_2026_11](../LYRIC_PIPELINE_2026_11.md) §5.2。

## 6. 行级文本补词通道（`LyricsResolver`）—— 与时间轴通道并列

两条通道都从同一个 `MediaAdapter.snapshot()` 出发，但目标不同：`LyricsResolver` 给**行级 LRC 文本**（喂 `lyrics`），`LyricTimelineProvider` 给**词级时间轴**（喂 `lyricTimeline`）。

| 项 | `LyricsResolver` | `LyricTimelineProvider` + `LyricCatalog` |
| --- | --- | --- |
| 产出 | 文本 LRC（String） | JSON 时间轴 + `LyricTimeline` |
| 缓存目录 | `filesDir/media-lyrics/<sha1>.lrc`（`:441`） | `filesDir/lyric-timeline/<sha1>.lyric.json`（`LyricCatalog.java:133`） |
| key 的秒数 | `Math.round(durationMs / 1000.0)`（`:170`） | `durationMs / 1000` 截断（`LyricCatalog.java:146`） |
| 打分阈值 | `ACCEPT = 2.0`（`:40`） | `ACCEPT = 3.0`（`LyricCatalog.java:211`） |
| 超时 | 连接 2500 ms / 读取 3000 ms（`:37-38`） | 3000 / 4000 ms（`:52-53`） |
| 文本上限 | `MAX_LYRICS = 131072`，响应 `MAX_RESPONSE = 262144`（`:35-36`） | 响应 262144（`:54`） |
| 内存上限 | 16 条（`:58-63`） | 16 条（`:34`） |
| miss TTL | 30 min（`:39`），另有 `misses.size() > 64` 全清（`:105`） | 30 min（`:35`） |
| 线程名 | `uni-lyrics-resolver`（`:54`） | `uni-lyric-timeline`（`:55`） |
| 目录 | netease → qq → kugou（`:204-237`） | 4 家，来源优先（`:236-250`） |

`LyricsResolver.cached()` 只查内存，从不阻塞（`:75-80`）；`request()` 先判内存/miss/`pending` 去重（`:88`），再切后台（`:92-96`）。命中才回调 `changed`（`:109`），所以「补词成功」会触发一次快照推送。

## 8. 如何新增一个歌词源（checklist）

以新增 provider `foo` 为例，按下面顺序改；缺一步就会出现「目录命中但词不出现」的沉默失败。

1. **`LyricCatalog`：加 provider id 常量与顺序**
   - 新增 `public static final String FOO = "foo";`（对照 `LyricCatalog.java:46-49`）；
   - 加进 `ORDER`（`:51`）—— 决定「播放来源优先之后」的兜底顺序；
   - `label(FOO)` 给中文名（`:75-81`）；
   - 若该播放器有专属包名，补 `providerForPackage`（`:65-73`）。

2. **`LyricCatalog`：实现 `fetchFoo(...)` 并在 `fetch()` 分派**
   - `fetch()` 里加 `if (FOO.equals(provider)) return foo(title, artist, durationMs, words);`（对照 `:252-260`）；
   - 所有 HTTP 只能走 `get`/`post`/`body`（`:501-513`），自动获得 3 s/4 s 超时与 256 KB 上限；
   - 打分只用 `score(...)` + `ACCEPT`（`:184-209`、`:211`），不要自造阈值；
   - 返回 `LyricTimeline`；行级用 `LyricTimeline.parse(plain, translation, "", "")`，词级用 `parse(plain, translation, enhanced, "")` 或 `parseEnhanced(enhanced)`。

3. **`LyricCodecs`：若容器是私有格式，加解码器**
   - 新方法返回**增强型 LRC body 字符串**，失败返回 `""`（绝不抛异常，类注释 `LyricCodecs.java:31-33`）；
   - 复用 `inflate`（`:522-543`，已有 10 MB 上限）、`base64`（`:552-591`，API 26 以下不能用 `java.util.Base64`）、`fractionMillis`（`:468-475`）、`textBeforeMarkers`（标记在词后）/`wordsToEnhanced`（标记在词前）；
   - 密钥与 `KRC_KEY`/`QRC_KEY`/`KUWO_KEY` 放同一处常量区（`:37-45`），不要散落在方法里；
   - 若带语言标签或独立翻译文档，参考 `kugouLanguage`（`:87-91`）、`kugouTranslation`（`:114-151`）、`enhancedToPlain`（`:371-383`）。

4. **`MediaAdapter`：只在需要时改**
   - 一般**不用改**：`LyricTimelineProvider.resolve(...)` 已按 key 缓存，provider 选择在 `plan(owner)` 里完成；
   - 只有当新源需要「额外上下文」（比如专用 Cookie、账号 token）才在 `MediaAdapter` 里加读取，并通过 `LyricCatalog` 构造参数传入（**注意**：当前 `LyricCatalog` 构造只接 `cacheDir`，加参数要同步改 `LyricTimelineProvider.java:50-51`）；
   - **不要**新增快照键：`lyricTimeline`/`lyricTimelineLabel`/`lyricTimelineWords` 三个键的契约已固定（`MediaAdapter.java:420-422`），Flutter 侧按这三个键解析。

5. **清缓存/失配处理**
   - 若改了 `LyricCatalog.key()` 的格式，必须同时把 `CACHE_VERSION` 从 `2` 提到 `3`（`LyricCatalog.java:55`、读校验 `:98`），否则旧缓存会被当作有效命中；
   - 改 provider id 字符串也要提版本（缓存里存了 `provider` 字段并在 `:100` 校验）。

6. **测试（必须加）**
   - `app/android/app/src/test/java/.../lyrics/LyricTimelineTest.java`：新格式的解码正确性（对照 `krcDecodesToWordTiming` `:67-90`、`markersThatFollowTheirWordAreSlicedForward` `:92-98`）—— 断言输出 body 的**逐字精确形态**，不要只断言 `contains("(1000,500,0)")` 之外的东西；
   - 打分与 key：加 `score(...)` / `key(...)` 的边界用例（同名不同歌手、时长差 >10 s、版本词去噪）；
   - 若无网络依赖，用固定 JSON 字符串喂 `LyricCatalog.fromJson`（`:589-612`）验证缓存回填；
   - `app/test/lyric_timeline_test.dart`：如果新源会改变 payload 形态（例如新增字段），补一条 `LyricTimeline.parse` 的容错断言（对照 `:65-71`「unusable payloads degrade to empty」）；
   - 若新增了 Dart 侧渲染，`LyricKaraokePanel` 的 widget 测试要覆盖「空时间轴 → `emptyReason`」分支（`lyric_timeline_test.dart:93-108` 现有写法可参照）。

7. **文档**：更新 05/06 两篇里的 provider 表（§5.1、§5.4）与编码表（§4），否则下一个智能体会按旧表判断能力。
