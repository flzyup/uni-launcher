# 10 · Android 原生组件与权限参考（UNI 桌面）

本文回答三类问题：这个 App 到底往系统里注册了哪些组件、每条权限被哪段代码真正用到、以及「某个能力在车上没反应」时是权限没给还是签名不对。
读者是后续 AI 智能体：先读第 1 节拿到组件/权限的定位坐标（`文件:行号`），再跳到对应小节；不要凭本文之外的记忆补全类名或权限名。
所有 `文件:行号` 对应仓库 `D:\PO\uni-launcher` 当前源码；路径省略公共前缀 `app/android/app/src/main/java/xyz/i4o/uni/launcher/`（下文简称 `…/`），Dart 侧写作 `app/lib/...`。
无法从代码证实的结论都标 `待确认：…`，这类条目不要当结论用。
多引擎（主窗口 / 全局底栏 / 面板）的通道归属见第 3 节——这是本仓库最容易踩的坑，先看那节再看组件表。

### 1.1 几个容易被误读的组件事实

- **`MainActivity` 同时是 HOME 应用和普通应用**：一个 activity 挂了两套 filter（L54、L55），所以系统既会在「全部应用」里显示它，也会把它当桌面候选。`android:launchMode="singleInstance"`（L52）意味着它独占一个 task；代码里还额外做了「新实例把上一个 finish 掉」的兜底（`MainActivity.java:195-196`）。
- **`GlobalDockService` 不是启动器服务**：manifest 没给它任何 filter（L66），只有 `ensureStarted()` 会拉起（`GlobalDockService.java:51-56`），并且要求两个条件同时成立——`globalDockEnabled` 为真且 `Settings.canDrawOverlays()` 为真（`:53`）。
- **`MediaAccessService` 是空壳**：`MediaAccessService.java` 只有 4 行，注释写明「permission boundary only, reads nothing」（`:3`）。它存在的唯一目的是拿到通知使用权（媒体会话信息来源），别指望从它身上找到通知内容处理逻辑。
- **`ClusterLyricsService` 一行日志都没有**：全文件没有 `Log.*` 调用，所有诊断都走 `report()`/`status()`（见第 3.3 与 12 号文档）。排查副屏问题只能读 `clusterLyricsStatus` 的 `report` 字段。
- **两个 provider 都是 `exported=false` + `grantUriPermissions=true`**（L72、L73）：外部安装器能读，是因为安装 Intent 上带了 `FLAG_GRANT_READ_URI_PERMISSION`（`MainActivity.java:129`）。

## 3. 三个 FlutterEngine

### 3.1 引擎怎么造

`LauncherEngines` 是 application 级的工厂：一个 `FlutterEngineGroup`，每个入口一个 engine，共享 GPU/字体/快照资源，但**各自独立的 Dart isolate 与通道实例**（`LauncherEngines.java:9-29`）。

- `main` → `DartExecutor.DartEntrypoint.createDefault()`（`:19`）
- 其它入口 → `DartEntrypoint(findAppBundlePath(), "package:uni_launcher/main.dart", entrypoint)`（`:20`）
- 存活数 `liveCount()`（`:30`），会出现在底栏状态里（`GlobalDockService.java:67` 的 `liveFlutterEngines`）

### 3.2 三处引擎对照

面板里能开哪些页签是白名单：`apps, climate, media, vehicle, navigation, music-picker, uni-menu, transfer, cleaner`（`GlobalDockService.java:352`），不在名单里的 value 不会建面板。

### 3.3 同名通道 ≠ 同一实例（本仓库最大的坑）

通道名 `xyz.i4o.uni.launcher/platform` 在三处引擎里各注册了一次：

- 主窗口：`MainActivity.java:101`
- 底栏/面板：`GlobalDockService.java:236`

但底栏/面板那份只实现四个方法（`GlobalDockService.java:239-248`），`clusterLyricsDisplays/Status/Apply` 只在主窗口实现（`MainActivity.java:152-165`）。于是：

1. 任何代码在**底栏/面板**里调用 `clusterLyrics*`，拿到的是 `notImplemented`（`GlobalDockService.java:248`）；
2. Flutter 侧抛 `MissingPluginException`；
3. `ClusterLyrics` 把异常吞成默认值：列表 `const []`（`app/lib/platform/cluster_lyrics.dart:121-123`）、状态 `unknown`（`:133-135`）、应用失败文案 `原生投射服务不可用`（`:157`）。

结论：**同名通道在不同引擎里是不同实例，状态不共享**。要共享的只有三种东西——

| 共享物 | 位置 | 说明 |
|---|---|---|
| `LauncherRuntime` 单例 | `LauncherRuntime.java:90`（`get()`），prefs `launcher`（`:104`） | 唯一数据源；三个引擎各自 `LauncherController` 却读同一份快照 |
| 歌词投射状态 | `LyricCast.java:16`（`static volatile State`） | 视图与卡片读同一份，所以副屏填充边缘和桌面一致 |
| 频谱 / 氛围灯 broker | `SpectrumBridge.java:93`（broker 跨引擎共享）、`AmbientLightBridge.java:43`（`sharedWriter`） | 多个组件共享一个采集器/写入器，避免重复开 Visualizer |

排查口诀：**面板里报 `notImplemented` 不一定是 bug，先看那个方法是不是只在主窗口实现。**

## 4. 开机链路

系统上有两条独立的开机链，别混。

### 4.1 原车分批广播链（`0ST/1ST/2ND/3RD`）

原车 Launcher 会按批次发自己的开机广播，本 App 借 `3RD` 这一批做静默 OTA 检查。

| 步 | 位置 | 行为 |
|---|---|---|
| 1 | `OtaBootReceiver.java:14` | 只接受 `com.ecarx.intent.action.EAS_LAUNCH_BAT_3RD`，其它忽略 |
| 2 | `OtaBootReceiver.java:15` | `startService(OtaBootService)` |
| 3 | `OtaBootService.java:10` | `MainActivity.requestBootUpdateCheck()` |
| 4 | `MainActivity.java:102` | 通过 `ota-events` 通道 `invokeMethod("boot-check")` 打到 Dart |
| 5 | `app/lib/ota/update_controller.dart:78-83` | Dart 收到后跑一次检查 |

App 自己也会在 `onResume` 里把这条链补齐，不依赖原车是否真的发过广播：`scheduleLauncherBroadcasts`（`MainActivity.java:353`）→ 4 次自广播，延迟 `0/1000/6000/11000` ms（`OtaBootReceiver.java:26-27`），并用 `boot_count` 与 `broadcastBoot` 比对，做到「每次开机只跑一次」（`:20-24`）。发广播抛 `SecurityException` 时不崩，只打日志（`:33`）。

### 4.2 系统开机广播链（`LOCKED_BOOT` → `BOOT` → `USER_UNLOCKED`）

这条链负责「开机后桌面还是不是我们」和「底栏有没有起来」。

| 步 | 位置 | 行为 |
|---|---|---|
| 1 | `GlobalDockBootReceiver.java:9-12` | 接三个 action，全部受理 |
| 2 | `GlobalDockBootReceiver.java:15` | 只有 `BOOT_COMPLETED` 才 `GlobalDockService.ensureStarted`（直接启动阶段不能建悬浮窗） |
| 3 | `GlobalDockBootReceiver.java:17` | 排 5 次延迟复检：`1000/4000/8000/16000/32000` ms（`:6`），action 为 `xyz.i4o.uni.launcher.action.RESTORE_HOME`（`:5`） |
| 4 | `DefaultHomeAlarmReceiver.java:10` | 收到闹钟后打 `UniHome delayed check` |
| 5 | `GlobalDockBootReceiver.java:32-41` | `goAsync()` + 后台线程跑 `DefaultHomeGuard.restoreIfNeeded()`；只有「恢复成功且不是直接启动阶段」才调 `dismissResolver()` 关掉系统「选择桌面」弹窗（`:36-37`） |
| 6 | `DefaultHomeGuard.java:17-56` | 读当前 home（日志 `UniHome current home=`，`:30`），不等就反射 `replacePreferredActivity`（`:47-52`），结果打日志（`:56`） |

`directBootAware="true"`（manifest L74）意味着 `LOCKED_BOOT_COMPLETED` 到达时用户数据可能还没解密——这条链上**不要读用户存储**。现有代码在直接启动阶段只做 `ensureStarted`（`GlobalDockBootReceiver.java:15` 只在 boot 分支），是安全的；新增逻辑要守这个约束。

### 4.3 桌面进程自己的开机任务

`MainActivity.onCreate` 里排三件事（`MainActivity.java:186-187`）；`GlobalDockService.onCreate` 也会再排一次（`GlobalDockService.java:196`）——重复调用是安全的，因为每条计划按「每个开机周期只触发一次」去重（`BootLaunch.java:81-94`）。

| 任务 | 入口 | 关键限制 |
|---|---|---|
| 开机自动播放 | `LauncherRuntime.scheduleBootAutoPlay`（`LauncherRuntime.java:551`） | 依赖媒体会话；demo 模式跳过 |
| 开机自启动应用 | `BootLaunch.schedule()`（`BootLaunch.java:182`） | 只在开机后 **10 分钟**窗口内动作（`:24`、`:187`），单条最大延迟 600 s（`:22`），最多 12 条计划（`:23`），每条计划每个开机周期只触发一次（`fired` 列表去重 `:81-99`，跳过已触发 `:198`），计划间 250 ms 错峰（`:202`）；demo 模式跳过（`:216`） |
| 开机拉无线 adb | `WirelessAdb`（`LauncherRuntime.java:570`） | 预先 `bootWirelessAdb`（`WirelessAdb.java:39`）；最多 6 次、每 20 s 重试（`:40-41`）；缺桥组件时给固定文案（`:143-145`） |

## 5. 签名与实车证书

### 5.1 为什么模拟器包在车上等于「车控全废」

`android.car.permission.CAR_VENDOR_EXTENSION` 的保护级别是 `signature|privileged`（`app/README.md:76-78`、常量 `OfficialCarContract.java:42`）。证书对不上时：

1. 权限不授予 → `OfficialCarReader.permitted()` 为 false（`OfficialCarReader.java:399`，判定处 `:421`）；
2. 车控 SDK 句柄不创建 → `initializeOnMain` 走失败分支（`:419-440`），文案 `车辆厂商读取权限未授权`（`:421`）或 `官方车辆接口初始化失败：…`（`:438`）；
3. 界面看起来「这车没这功能」，实际是签名问题。

`build.gradle.kts` 里的 `uniLocal` 签名配置就是给模拟器/开发用的（`:46-60`），注释明确写了实车包要另外签（`:49-55`），debug 与 release 都指向它（`:63`、`:67`）。**所以 `flutter build apk --release` 出来的包，在车上车控一定不可用**，这不是 bug。

### 5.2 `tools/sign_car_apk.py` 干什么

它就是「把开发包变成实车包」的那一步，做四件事：

| 步骤 | 代码 | 说明 |
|---|---|---|
| 1 | `tools/sign_car_apk.py:79-89` | 找 `platform.pk8` + `platform.x509.pem`。查找顺序：`--toolchain` → `IP753_SIGNING_DIR` → `/data/tools/linkco-android/ip753-signing` → `<workspace>/cardesk/platform-key`（`:79-84`）；密钥不入库（`:77-78`） |
| 2 | `tools/sign_car_apk.py:92-107` | 找 java 与 Android SDK（apksigner 用）。`JAVA_HOME` 为空时退回 `shutil.which('java')`（`:95`） |
| 3 | `tools/sign_car_apk.py:109` 起 | 用 apksigner 重签 |
| 4 | `tools/sign_car_apk.py:15` | 顺带注入导航栏 inset 资源（`build_nav_insets`） |

输出默认落在 `dist/UNI-Launcher-<版本>-IP753.apk`（`tools/sign_car_apk.py:19-24`），刻意与原始构建产物分开，避免装错包。脚本拒绝 `--input` 与 `--out` 相同（`:36-37`），即**不允许覆盖开发包**。

### 5.3 覆盖安装与版本号

- 两种证书的包**不能互相覆盖**；同证书的后续版本可以正常升级（`app/README.md:105`）。
- 分 ABI 构建的 versionCode 由 Flutter 加 ABI 前缀（arm64 形如 2007、x86_64 形如 4007，`app/README.md:107`）；`app/android/local.properties` 当前记 `flutter.versionName=0.7.6`、`flutter.versionCode=54`。
- 判断手上这台装的是哪个包：

```powershell
$adb = 'D:\platform-tools\adb.exe'
& $adb -s $Serial shell dumpsys package xyz.i4o.uni.launcher |
  Select-String 'versionName|versionCode|signatures'
```

`signatures=` 后面的十六进制串两台设备不会相同；与实车包对比即可确认装的是开发证书包还是平台证书包。`待确认：` 车机 ROM 上 `dumpsys package` 是否被裁剪（本机模拟器与 192.168.22.26 上均可用）。

### 5.4 签名相关的其它落地点

- `otaInstall` 会核对「包名相同 + versionCode 更大 + 签名完全一致」三者，任一不满足直接 `SecurityException("package identity")`（`MainActivity.java:125`），Dart 侧显示 `安装包不兼容或签名不一致`（`app/lib/ota/update_controller.dart:522`）。
- 新版本启动后会清理已安装的 OTA 缓存（`cleanupInstalledOta`，`MainActivity.java:64-78`），同样以签名数组相等为前提（`:71-72`）。
- 无线 adb 桥是另一个独立 APK（`xyz.i4o.uni.adbbridge`，`WirelessAdb.java:36-37`），靠同签名 + `xyz.i4o.uni.adb.BRIDGE` 权限通信；桥没装时状态是「缺少桥组件」，不是权限问题。
