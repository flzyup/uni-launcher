# UNI 桌面 · 原生通道接口契约

这份文档把 Flutter 与 Android 原生之间所有 MethodChannel / EventChannel 的**线上真实形状**固化下来：谁注册、谁调用、参数是字符串还是 Map、返回值是 JSON 文本还是可序列化对象、哪些 code 会走 `result.error`。
智能体在改 Dart 侧调用、加原生方法、或在原生侧改返回值之前，先查这里的表；凡是本文件没写的通道/方法，就是仓库里不存在，不要去"补全"。
最容易被写错的几件事：`snapshot` / `action` / `viewport` 三个方法的 arguments 和返回值**都是 JSON 字符串**，不是 Map；`action` 超过 8192 字节直接 `invalid`；同一个通道名 `xyz.i4o.uni.launcher/platform` 有**两套实现**（主窗口 / 底栏窗口），方法集不同。
本文只描述接口，不描述业务逻辑；action 的名字与参数见 [02-action-router.md](02-action-router.md)。

### 2.1 `snapshot` —— 返回 JSON 字符串，不是 Map

```java
if("snapshot".equals(call.method)){
    updateSnapshot();result.success(cached);   // cached 是 String
    initialSettings=false;
}
```
`MainActivity:105-110`

- `cached` 是 `String` 字段，初值 `"{}"`（`MainActivity:49`），每次 `updateSnapshot()` 用 `state.toString()` 覆盖（`MainActivity:219`）。
- 因此 Dart 侧必须先 `jsonDecode`：`native_gateway:31` 就是 `jsonDecode(await methods.invokeMethod<String>('snapshot') ?? '{}')`。
- 首次调用会**消费**一次性 `initialSettings` 标志（`MainActivity:109`，写入点在 `decorate` 的 `MainActivity:255`）。
- 快照内容 = `LauncherRuntime.snapshotWithSettings(cursor)`（`LauncherRuntime:157`）再叠 `decorate` 的窗口几何（`MainActivity:233-260`）。顶层键清单见 §3。

### 2.2 `action` —— 唯一写命令入口，参数是 JSON 字符串

```java
else if("action".equals(call.method)){
    String raw=(String)call.arguments;
    if(raw==null||raw.length()>8192){result.error("invalid","Invalid request",null);return;}
    handle(new JSONObject(raw));result.success(null);
}
```
`MainActivity:147-151`

- arguments 是 **String**，内容 `{"action":"名字","value":…,"zone":…,"enabled":…}`；Dart 侧 `native_gateway:41-46` 用 `jsonEncode` 拼，键按需省略。
- 长度上限 8192 **字符**（不是字节），`null` 或超长 → `error("invalid","Invalid request",null)`。
- JSON 语法错误 → `new JSONObject(raw)` 抛 `JSONException` → 被 `MainActivity:167` 兜住 → `error("unavailable", …)`（不是 `invalid`）。
- 合法 JSON 但缺 `action` 键 → `optString("action")` 返回 `""`，所有分支都不匹配，**静默成功**（`result.success(null)`，无任何效果）。
- 业务成败**不通过返回值表达**：成功一律 `success(null)`，失败走原生 Toast（`LauncherRuntime:630`、`MainActivity:337`）或状态事件流。Dart 侧不要试图从返回值判断成败。
- 底栏实现的同名字面量文案不同：`error("invalid","操作无效",null)`（`GlobalDockService:244`）。

### 2.3 `viewport` —— 参数也是 JSON 字符串

`new JSONObject((String)call.arguments)`（`MainActivity:145`）。Dart 侧构造见 `launcher_shell:91-99`：`width`、`maxHeight`、`height`、`nativeHeightPx`、`dpr`、`page`、`settings`。原生只用 `settings` 和 `page`：
`rt.setDesktopContent(!flutterViewport.optBoolean("settings")&&flutterViewport.optInt("page")==0)`（`MainActivity:146`）。
同时原始 `flutterViewport` 会原样进入 `dumpsys --uni-state`（`MainActivity:329`），改字段名不会破坏接口，但会改变诊断输出。

### 2.4 `desktopPage`

`Number` → `int page`（非 Number 落 0，`MainActivity:140`）；副作用：`mapHost.preparePageChange()`（`MainActivity:141`，当前是空实现 `LiveNavigationHost:84`）、写 `flutterViewport.put("page",page)`、`rt.setDesktopContentSilently(page==0)`（`MainActivity:142-143`）。**不发事件**（Silently）。

### 2.5 `saveDesign`

返回值是 `Boolean`：`result.success(rt.saveDesign((String)call.arguments))`（`MainActivity:132`）→ `LauncherRuntime:159` → `saveDesignOnMain`（`LauncherRuntime:242-287`）。
被拒绝时返回 `false`（不是抛异常），Dart 侧 `native_gateway:51-52` 据此抛 `StateError('保存未完成')`。白名单细节见 [02-action-router.md](02-action-router.md) §"参数校验"。

### 2.6 `pickWallpaper` —— 异步 + 挂起

- 已有请求未完成 → `error("busy","图片选择器已打开",null)`（`MainActivity:134`）。
- 成功路径在 `onActivityResult`（`MainActivity:384-403`）：`startActivityForResult` 后把 `result` 暂存在 `wallpaperResult`，用户取消或 uri 为空 → `success(null)`（`MainActivity:389-392`）。
- 解码/裁剪/压缩在独立线程（`MainActivity:394-402`），失败 → `error("invalid-image","无法读取这张图片",null)`（`MainActivity:400`）。
- 成功返回 `Map`：`path`（`filesDir/wallpapers/custom-<ms>.jpg`）、`luminance`（0..1，32×18 采样）（`MainActivity:443-455`）。
- `onDestroy` 时若仍挂起会 `success(null)`（`MainActivity:499`）。

### 2.7 错误 code 汇总（全部，只有这 5 个）

| code | message | 触发条件 | 位置 |
| --- | --- | --- | --- |
| `invalid` | `Invalid request` | `action` 参数为 `null` 或长度 > 8192 | `MainActivity:149` |
| `invalid` | `操作无效` | 同上，底栏实现 | `GlobalDockService:244` |
| `busy` | `图片选择器已打开` | `pickWallpaper` 重入 | `MainActivity:134` |

`notImplemented` 只在方法名不认识时触发（`MainActivity:166`、`GlobalDockService:248`）。

### 3.1 顶层键

| 键 | 类型 | 何时出现 | 位置 |
| --- | --- | --- | --- |

| `recentTasks` | `List` | 仅面板 + `panel=="recents"` 且列表对象变化 | `GlobalDockService:321-329,348` |

### 3.2 增量约定（智能体最容易踩的坑）

1. 快照是**按分组增量**的：`apps` / `savedDesign`+`appNames` / `systemSettings` 可能整块缺席，用 `partial` 判断（`LauncherRuntime:216`）。
2. `media.artwork`、`media.lyrics` 缺席是正常状态，**不表示没有封面/歌词**——只有 media 分组变化时才带（`LauncherRuntime:207`）。
3. 底栏/面板快照**没有** `systemSettings`（走 `snapshot()` 而非 `snapshotWithSettings()`，`GlobalDockService:344` vs `LauncherRuntime:154-157`）。
4. 事件流有去重：`*AtMs` / `*AtElapsedMs` 时间戳被抹成 `"t":0` 后比较签名，内容没变就不发（`MainActivity:302-315`、`GlobalDockService:314-319`）。
5. 没有订阅者时不构建快照（`MainActivity:297`），所以"我先发 action 再看 events"会漏一帧。
6. 事件取消订阅后游标被重置（`MainActivity:172-177`），下一个订阅者首包会重发全部静态分组。
7. **主窗口**在静态分组未变化且包体 > 65536 字符时会打 `UniPerf` 警告（`MainActivity:222-223`）——这是"payload 泄漏回增量包"的哨兵，改动快照结构时注意别触发。

## 4. `clusterLyrics*` ↔ `ClusterLyricsService` 对应关系

| 通道方法 | 参数键（Dart→原生） | 参数类型 | 缺失/类型不符时的取值 | 原生入口 |

| `clusterLyricsStatus` | 无 | — | — | `ClusterLyricsService:164` |

- `apply` 的 arguments 若不是 `Map`，取 `Collections.emptyMap()`（`MainActivity:157`），效果等同于"关闭投射"（`enabled=false`、`displayId=-1`）。
- `apply` 返回的是**回读**：`result.success(ClusterLyricsService.status(this))`（`MainActivity:165`），形状与 `clusterLyricsStatus` 完全一致，Dart 侧两个方法可以共用一个解析器（`cluster_lyrics:128,145`）。
- `status` 的字段：`enabled:Boolean`、`displayId:int`、`displayName:String`、`fontSp:float`、`solidBackground:Boolean`、`report:String`（`ClusterLyricsService:167-172`）。
- `displays` 的元素字段：`id:int`、`name:String`、`label:String`、`presentation:Boolean`、`width:int`、`height:int`、`densityDpi:int`（`ClusterLyricsService:193-199`）。
- **坑：prefs 键名与通道字段名不同**。持久化在 `SharedPreferences("cluster-lyrics")`（`ClusterLyricsService:48`），键是 `enabled`/`displayId`/`displayName`/`fontSp`/**`background`**（`ClusterLyricsService:49-53`）——`solidBackground` 落盘叫 `background`。直接改 prefs 的脚本要按这个键。
- `apply` 会副作用启动/停止 `ClusterLyricsService` 本身：`enabled=false` → `stopService` 并置 `report="已关闭"`（`ClusterLyricsService:139-142`）；后台启动被拒 → `report="后台启动被系统拒绝，回到桌面再试"`（`ClusterLyricsService:146-147`）。
- `report` 取值还会由投屏流程写入（`ClusterLyricsService:220,305,329,335`；`lastReport` 初值 `"未启用"`，`ClusterLyricsService:61`）。完整取值集合未穷举——**待确认：`report` 是否有稳定枚举**。

**两条派发链不一样，这是最容易踩的不对称**：

- 主窗口：`MainActivity.handle` 先调 `GlobalDockService.handleCommand`（`MainActivity:263`），所以**底栏专属 action 在主窗口也能用**。
- 底栏：`GlobalDockService` 先处理自己的，再调 `runtime.handle`（`GlobalDockService:246`），**不会**经过 `MainActivity.handle`，所以只存在于 `MainActivity.handle` 的 action 在底栏发是静默无效的（`MainActivity:268,275-283`）。
