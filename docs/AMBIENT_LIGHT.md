# 音乐律动氛围灯

把正在播放的音乐频谱换算成颜色与亮度，下发到车机氛围灯通道。

## 功能

- 桌面设置新增「氛围灯」标签页：开关、颜色模式、灵敏度、车机亮度、亮度上下限、固定色。
- 实时预览：当前颜色、亮度条、频谱条，与下发给车机的颜色同源。
- 三种颜色模式：
  - **跟随低频**：取低频段（24 段对数频谱里的前 4 段，约 60–150 Hz）里最响的那一段决定色相，鼓点一响灯就跳。
  - **跟随频谱**：全部频段按能量做**圆周加权平均**决定色相，像一条彩虹随音乐流动。
  - **固定色**：色相固定，颜色仍随电平明暗变化。
- **音乐的强弱体现在颜色的明暗上**：电平换算出 `明暗 = 下限 + (上限 − 下限) × 电平^(1/灵敏度)`，再把颜色整体按这个比例缩放。灵敏度越高，微弱的声音也越能点亮氛围灯。
- **车机亮度是用户的绝对值**：车机只有「高／低／关」三档，写进去的是「车机亮度」滑杆的值（0–100），不是频谱折算值——否则用户拖完滑杆，下一帧就被覆盖回去了。
- 静音时保留上一次的色相，避免灯在没有声音时乱跳。
- **颜色是「流动」的，不是「跳」的**：频谱 10 Hz 直接算颜色的话，色相会在频段之间跳、亮度会跟着频谱抖。中间加一层**动感层**（`AmbientMotion`）：色相走**最短路径**并限速 90°/秒，亮度**快起慢落**，低频起拍再叠一个衰减脉冲。
- **频谱分辨不出低频时不装作有信息**：采集点数太少时，低频四段会塌进同一个 FFT bin，四段功率永远相等 ⇒「取最响的那一段」永远取第 0 段 ⇒ 色相恒为 0°（红）、亮度钉死。这时改用低频**强度**映射色相（安静 = 深紫，响 = 橙红），宁可粗但真实，也不要卡住不动。

## 频谱采集：为什么以前只会显示「等待音乐播放」

实车反馈：氛围灯**亮着**（说明车机通道、功能号、写入都通了），但**颜色一直不变**，状态行一直停在「等待音乐播放」。

根因不是氛围灯，是**频谱这一侧没有数据**，而界面把三种完全不同的情况显示成了同一句话：

| 实际情况 | 以前显示 | 现在显示 |
| --- | --- | --- |
| 缺 `RECORD_AUDIO` 权限 | 频谱需要录音权限 | 频谱需要录音权限 |
| 采集挂不上（通道被占 / ROM 不支持） | **等待音乐播放** | 频谱采集不可用（原生原因） |
| 采集在跑，但没听到声音 | **等待音乐播放** | 等待音乐播放 |
| 采集在跑，有声音 | 频谱采集中 | 频谱采集中 |

关键的一处：原生侧**以前只有「这一帧有信号」才推包**。于是「采集已经跑起来了但此刻没声音」和「根本没采到」在界面上完全一样。现在静音的帧也照推（10 Hz），状态才分得清；顺带也让灯在音乐停下时能按「快起慢落」慢慢暗下去——以前没有静音帧，灯会**冻在**最后一个颜色上。

### 车机 ROM 要求频谱走主线程

实车报的就是这一条：

```
频谱采集不可用（Methods marked with @UiThread must be executed on the main thread. Current thread: uni-audio-spectrum）
```

**AOSP 原版 `Visualizer` 并没有这个限制**（官方示例就是用后台 `HandlerThread` 轮询 `getFft()`），但车机 ROM 自己加了这个检查：把 `Visualizer` 的方法标成了 `@UiThread`，从后台线程调用就抛 `IllegalStateException`。

症状极具迷惑性：句柄**创建成功了**（所以诊断里采集来源是「输出混音」），第一次轮询 `getFft()` 才炸；异常被捕获后状态变成「采集不可用」，于是从头到尾**一帧都没采到**（`已收到 0/0 帧信号`）。

所以这里的采集**全程在主线程**：创建、设采集点数、启用、轮询、释放都在同一条线程上。

- 每帧的活很小（一次 1 KB 的 native 读 + 24 段求和），10 Hz 挂在主线程上完全负担得起。
- 顺带消掉了「轮询与释放并发」的风险：以前释放句柄和 `getFft()` 可能在两条线程上撞车（native 段 SIGSEGV）。现在全在一个线程上，不会再有。
- 释放也加了兜底：车机上万一连 `release()` 都受限，也只是这一次释放失败，不会把进程带崩。

### 采集路径：主路径 + 次选路径

| | 做法 | 状态 |
| --- | --- | --- |
| 主路径 | `Visualizer(0)` 抓全局输出混音 | 输出混音 |
| 次选路径 | 挂到正在播放的那个会话上（`audioSessionId` 靠反射） | 播放会话 |

- 次选路径在参照工程上实机验证过。`AudioPlaybackConfiguration.getAudioSessionId()` 是 **@hide**（公开 SDK 只有 `getAudioAttributes()`），所以要反射，因此启动时要放开隐藏 API（`HiddenApiCompat`，只影响本进程）。
- **挂不上就退到次选路径**：主路径抛异常时立刻试次选路径。
- **主路径挂上了却一直听不到声音**，而车机上确实有东西在播（播放配置里有活动会话）时，6 秒后改挂到那个会话上。
- **失败不是终局**：采集失败后每 3 秒重试一次（通道被别人占着、权限迟到都属于暂时性的）。以前失败一次就卡死到用户手动开关一次氛围灯为止。

### 不连 adb 也能查

车机上不方便连 adb，所以设置页自己带了一行诊断：

```
频谱：输出混音 · 采集点数 1024 · 48kHz · 已收到 1234/1234 帧信号 · 隐藏 API 已放开
```

- 「已收到 X/Y 帧信号」：X 是带信号的帧数，Y 是总帧数。**X 一直是 0** = 采集在跑但没听到声音；**Y 也是 0** = 采集根本没跑起来。
- 「隐藏 API」：不是「已放开」就说明次选路径用不了（拿不到会话 id）。
- 采集来源显示「输出混音」还是「播放会话」，直接告诉你走的是哪条路。

## 与 cardesk 实机版的对齐

cardesk 的氛围灯已在实车验证通过，本实现按它的模型逐条对齐：

| 行为 | cardesk（实机验证） | 本实现 |
| --- | --- | --- |
| 车机句柄 | `ensureFunction()` **每次使用时**懒解析 `getICarFunction()`，拿到才缓存 | `OfficialCarReader.borrowedFunctions()` 同样每次重试，拿到才缓存 |
| 车机亮度 | 用户的**绝对值**（`absoluteBrightness`） | 「车机亮度」滑杆的绝对值 |
| 频谱强弱 | `scaleByBrightness()` **缩放进颜色** | 同 |
| 颜色写入 | 只写**最新一帧**，中间帧丢弃 | 同 |
| 写失败 | 退避 1 秒，不按帧率重试 | 同 |
| 开关／亮度 | 「期望值 vs 已写值」三元组，每 3 秒重试到成功 | 同 |
| 采集点数 | 期望 1024（夹设备范围，被拒退回 512） | 同 |
| 采样率单位 | `normalizeSampleRate()`：车机报毫赫兹（48000000），标准设备报赫兹（44100），都归一成赫兹 | 同 |
| 动感层 | `AmbientMotion`：色相指数平滑 + 最短路径 + 限速 90°/秒；亮度快起慢落（attack 50 ms / decay 320 ms）；低频起拍脉冲（τ 170 ms，增益 0.45） | 同（纯 Dart 状态机，`app/lib/model/ambient_motion.dart`） |
| 低频分辨不出时 | `isBassUnresolvable()` ⇒ 改用强度→色相（冷 260° → 暖 20°） | 同 |
| 写频节流 | 最小间隔 100 ms + 幅度阈值 2 | 同（**旧版**）。**V2 改成 50 ms**：颜色在 60 Hz 上合成，10 Hz 的写入会把平滑重新切成台阶 |

> 句柄懒解析这一条是实车能不能亮的关键：`getICarFunction()` 在车机服务还没连上时返回 null，
> 而那正是应用启动那一刻的状态。早期只在 `connect()` 时取一次，
> 拿到的 null 被缓存住，于是整个进程生命周期里都「没有车机句柄」——
> 表现就是「连上了但车控没反应」。

## 频率轴：采集点数与采样率单位

频谱的「哪一段是低频」完全由 FFT 的频率轴决定，这一层错了不会崩，只会**静悄悄地读错频段**。

| | 44.1 kHz 下的 bin 间隔 | 60–149 Hz 的低频四段 |
| --- | --- | --- |
| 512 点 | 86.1 Hz | 四段**全部塌进同一个 bin**（bin 1） |
| 1024 点 | 43.1 Hz | 四段各占不同 bin（[1] / [1,2] / [2] / [2,3]） |

四段塌进同一个 bin ⇒ 四段功率**永远相等** ⇒「取最响的那一段」永远取第 0 段 ⇒
色相恒为 0°（红）、低频能量饱和 ⇒ 亮度钉死 —— 表现就是「灯是红的、拉满、一动不动」。

所以采集点数要 **1024**（夹到设备支持的范围里，设备只支持 512 就还是 512；设备报支持却实际拒绝时退回 512，别让整个采集起不来）。

采样率单位也要对：**车机 ROM 报的是毫赫兹**（`48000000`），标准设备报的是赫兹（`44100`）。
按固定单位算会让频率轴差 1000 倍（低频段实际读到 11–22 kHz 的齿音区）。
`SpectrumBands.normalizeSampleRate()` 把两者都归一成赫兹再算频率轴，
诊断里的 `sampleRateHz` 也报归一后的值。

采样率还要有**兜底**，三级取值：Visualizer 报的 → `AudioManager` 的输出采样率属性 → 默认 48 kHz。
没有兜底时，车机上只要 `getSamplingRate()` 返回 0，**每一段都会解码成 0**——
频谱从此永远静默，而界面什么也看不出来（灯会一直亮着、颜色一直不变）。

## 色相为什么用圆周平均

色相是**环形**的：359° 和 1° 只差 2°，算术平均却会得到 180°（青绿）——正好是最离谱的结果。所以频谱模式的色相按 `cos/sin` 做圆周平均，而不是直接求平均。

## 车机通道

氛围灯在车机端 `ecarx.adapterapi.jar` 里是一组**设置类功能号**，写法和空调属性一样：`setFunctionValue(功能号, 区域, 值)`。

| 我们要做的事 | 功能号 | 写入的值 |
| --- | --- | --- |
| 开关氛围灯 | `SETTING_FUNC_AMBIENCE_LIGHT_INTERACTIVE_EFFECT` | `1` 开 / `0` 关 |
| 主色来源 = 自定义色 | `SETTING_FUNC_AMBIENCE_LIGHT_MAINCOLOR` | `AMBIENCE_LIGHT_MAINCOLOR_SETCOLOR` |
| 颜色 | `SETTING_FUNC_AMBIENCE_LIGHT_COLOR_SET` | `0xRRGGBB` 打包 |
| 行车亮度 | `SETTING_FUNC_AMBIENCE_LIGHT_BRIGHTNESS_DRIVING` | `HIGH` / `LOW` / `OFF` |
| 静止亮度 | `SETTING_FUNC_AMBIENCE_LIGHT_BRIGHTNESS_STATIONARY` | `HIGH` / `LOW` / `OFF` |
| 点亮主区 | `SETTING_FUNC_AMBIENCE_LIGHT_MAINZONES` | `1` |
| 点亮上区 | `SETTING_FUNC_AMBIENCE_LIGHT_TOPZONES` | `1` |
| 点亮下区 | `SETTING_FUNC_AMBIENCE_LIGHT_BOTZONES` | `1` |
| 体验模式 = 自定义 | `SETTING_FUNC_AMBIENCE_LIGHT_EXPERIENCE` | `AMBIENCE_LIGHT_EXPERIENCE_CUSTOM` |

「互动效果」就是厂商那边的**音乐律动**；主色设成「自定义色」，颜色由我们按频谱算好写进去。

### 三个陷阱

1. **分区是三个独立功能号**。写主区**不会**带上区与下区，只写主区的话上/下分区（门板那圈 / 脚部）点不亮，所以开灯时三个分区都写。某个分区解析不到就跳过那一个，不拿别的分区的号顶替。
2. **亮度 `0` 是 `OFF`（把灯关掉），不是「最低档」**。厂商把 `0` 映射成 `OFF`，`LOW` 必须传 `BRIGHTNESS_*_LOW` 常量。亮度 0 按「关灯」处理，这是故意的。
3. **亮度有两套**：行车（`0x200A0700`）与静止（`0x200A0600`）是不同功能号，档位常量也各有一套。代码**两套都写同样的值**，这样车在动和车停着亮度一致。

### 数值一律按名字解析

厂商常量放在 `com.ecarx.xui.adaptapi.car.vehicle.IAmbienceLight` 与 `IVehicle` 里。本工程**不链接**车机 jar，所有常量都用反射**按名字**解析（`AmbientLightResolver`），解析不到就**不写**——猜一个数值去写别的功能，比不写更糟。解析结果带缓存，功能号句柄的类会作为最准的根类登记。

### 体验模式与自定义色的先后

厂商有**两个**互不相干的开关：`MAINCOLOR`（主色来源）和 `EXPERIENCE`（体验模式）。写自定义色之前先把体验模式置成 `CUSTOM`。「不置 `CUSTOM` 则自定义色不生效」这条因果关系厂商文档与源码都没有明说，属于**未验证**项；先置 `CUSTOM` 成本极低（一次写），因此保留。

## 架构与性能

> 下面是**旧版**链路的架构。**V2** 把它拆成了四层（感知 / 艺术 / 运动 / 输出），
> 见「[V2：动感引擎](#v2动感引擎与-cardesk-同构)」。

```
AudioSpectrumService（真实播放频谱，10 Hz / 24 段）
      ↓ 频段能量 + 整体电平
AmbientPalette（纯函数：频段 → 目标色相 + 目标明暗）
      ↓ 目标值
AmbientMotion（纯状态机：色相平滑 + 最短路径 + 限速，亮度快起慢落，起拍脉冲）
      ↓ 平滑后的色相与明暗
AmbientPalette.colorOf（纯函数：色相 + 明暗 → 缩放后的颜色）
      ↓ AmbientColor
AmbientLightService（MethodChannel）
      ↓
AmbientLightWriter（原生：按名解析功能号 → 写入车机）
```

- **颜色计算放在 Dart**：映射是纯函数，能用 `flutter test` 覆盖，不需要设备和真实 FFT。
- **动感层也是纯状态机**：只吃「上一帧状态 + 这一帧目标 + 时间差」，不碰 Android，所以整条曲线都能被单测覆盖。时间差取真实值（单调时钟），平滑系数 `1 − e^(−dt/τ)` 与帧率无关。
- **原生只负责执行**：**车机写入**在专用后台线程，绝不占用 Flutter 平台线程。（**频谱采集**相反：车机 ROM 要求 `Visualizer` 走主线程，见上。）
- **写频节流**：旧版是最小间隔 100 ms（= 频谱帧率）+ 颜色变化幅度 2；**V2 改成 50 ms**（20 Hz），因为颜色在 60 Hz 上合成，10 Hz 的写入会把平滑重新切成台阶。幅度阈值必须小：动感层之后每帧颜色只挪一点点（色相最多 9°），阈值大就会把平滑重新切成台阶，灯又开始跳。折算后档位没变就不再重写亮度，否则每帧都会写一次车机 IO。
- **只写最新一帧**：频谱 10 Hz，车机写得慢的话队列会越堆越长（越堆越慢，越慢越堆）。颜色写线程只取**最新**的一帧，中间帧丢掉——颜色本来就是「当前该是什么颜色」，补写历史帧没有意义。
- **失败要退避**：写失败后等 1 秒再试。频谱 10 Hz，不退避就是每秒 10 次同步 binder 调用去撞车机的钉子。
- **开关与亮度会重试**：开灯不是一次写，而是「主色来源 + 体验模式 + 三个分区 + 互动效果」一串写。车机服务是异步连上的，第一次几乎必然失败，**必须每 3 秒重试到成功**——否则互动效果永远没打开，后面写的颜色没有载体，灯就是不亮。
- **单写者**：桌面、底栏、面板是三个 Flutter 引擎，但只有桌面引擎驱动氛围灯，原生侧也只保留一个写者。三个引擎共用同一份持久化设置。
- **频谱按需采集**：氛围灯打开时才向频谱服务申请数据；关闭时释放。频谱本身需要 `RECORD_AUDIO` 与 `MODIFY_AUDIO_SETTINGS`，没有授权时只显示状态，不采样。
- **预览不重建设置页**：实时颜色走独立的 `ValueNotifier`，只有色块、亮度条和频谱条重绘。
- **状态是活的**：原生侧在「能不能用 / 为什么不能用 / 上一次写成功没有」变化时主动推给 Dart；设置页另外每 5 秒复查一次兜底。开机瞬间读到的那句状态**不会**一直挂到界面上。

## 排查：三种失败长得不一样

界面上的状态行直接说原因，但车机上更精确的入口是原生诊断：

```sh
adb shell dumpsys activity xyz.i4o.uni.launcher/.MainActivity --uni-state
```

`ambientLight` 段里：

| 字段 | 含义 |
| --- | --- |
| `handlePresent` | 借到的车机 `ICarFunction` 句柄在不在。`false` = 车机服务没连上，或这个应用没拿到厂商权限 |
| `switchApplied` | 开灯序列（主色来源 + 体验模式 + 三个分区 + 互动效果）成功过没有。`false` 而 `handlePresent` 为 `true` = 功能号解析不到或写入被拒 |
| `resolvedIds` | 按名解析到的功能号与档位常量，一目了然 |
| `unresolved` | 解析不到的常量名。**空数组 = 功能号全解析到了**，问题在写入 |
| `lastWrite` | 最后一次写入：写的是哪个功能号、什么值、成功没有、失败原因 |
| `reason` | 上面那句话的中文版，界面显示的就是它 |
| `colorWrites` / `brightnessWrites` / `enableWrites` | 尝试次数（不是成功次数）。涨了说明链路在跑 |

`audioSpectrum` 段里：

| 字段 | 含义 |
| --- | --- |
| `captureSize` | 实际拿到的采集点数。**期望 1024**；若还是 512，说明这台车只支持 512，低频四段会塌进同一个 bin（色相退化成强度曲线） |
| `sampleRateHz` | 归一后的采样率（赫兹）。车机上是 48000 |
| `signalFrames` | 采到过信号的帧数。一直是 0 = 根本没抓到声音（权限没给 / 输出混音拿不到） |
| `peakLevel` | 当前整体电平 |

日志：

```sh
adb logcat -s UniAmbient
```

三种典型结论：

1. `handlePresent: false` → **车机服务没连上**。查两件事：
   - **签名**：实车包必须用 platform 证书签（`tools/sign_car_apk.py`）。`CAR_VENDOR_EXTENSION` 是 `signature|privileged`，证书对不上就没有权限，车控 SDK 根本不创建——现象和「没接氛围灯」一模一样。
   - **权限**：厂商权限 `android.car.permission.CAR_VENDOR_EXTENSION` 与车辆服务本身。
2. `handlePresent: true` + `unresolved` 里有名字 → **功能号按名解析不到**。该名字对应的常量在这台车机上不存在（固件差异）。
3. `handlePresent: true` + `unresolved` 为空 + `lastWrite.ok: false` → **车机拒绝了写入**。功能号对了但值不被接受，或者写入时机不对。

## 上车复测步骤

1. 装**实车签名包**（`tools/sign_car_apk.py` 产出的 platform 证书版本，不是开发证书包），开桌面设置 →「氛围灯」。
2. 打开「跟随音乐律动」开关，**等状态行变成「频谱采集中」**。中间会经过「正在点亮车机氛围灯」（车机接受开灯序列）和「等待音乐播放」（采集在跑、还没听到声音）。
3. 放音乐，看界面上的颜色与明暗是否随节奏变；再看诊断行里「已收到 X/Y 帧信号」的 X 有没有涨。
4. 看灯：三个分区是否都亮，颜色是否跟着变。
5. 如果状态行停在「频谱采集不可用」或「已收到 0/0 帧信号」，把**状态行 + 诊断行两行字**拍下来发回来——这两行里有采集来源、采集点数、采样率、隐藏 API 状态和原生失败原因，比 adb 的输出还直接。

实车验证过程中查出并修掉的问题，都是车机特有行为，模拟器复现不了：

1. **车机 ROM 把 `Visualizer` 的方法标成了 `@UiThread`**：后台线程调用 `getFft()` 会抛

2. **采样率单位**：车机报毫赫兹（48000000），标准设备报赫兹（44100），固定按一种算会让频率轴差 1000 倍。

## V2：动感引擎（与 cardesk 同构）

### 为什么重做

旧版链路（下面统称**旧版**）在实车上是通的，但观感被评价为**「灯在跳，不是灯在流动」**：

- 频谱 10 Hz，一帧算一个颜色，一帧写一次车机 ⇒ 颜色本身就是**台阶**；
- 旧版配色是 HSV + 线性 RGB 缩放，实测**单步跳变 ΔE00 ≈ 9.8~32.5**；
- 色相靠「挑最响的那一段」，段一换色相就跳；
- 亮度是「下限 + (上限−下限)×电平^(1/灵敏度)」的线性映射，母带压得响的歌**所有频段都在 0.7 以上** ⇒ 明暗变化只剩一点点。

V2 把这条链路拆成**四层**，每层只做一件事，而且各层的时间尺度**故意错开**。

### 分层

```
AudioSpectrumService（真实播放频谱，10 Hz / 24 段，绝对 dB 标定）
      ↓ 频段能量（绝对 dB）
SpectrumPerception（感知层：每段自适应参考 τ=2s + 全局静音门）
      ↓ 相对频段 0..1（每段的平均水平落在 0.5）
AmbientPalette（艺术层：质心色相 / 明度区间 / 彩度）
      ↓ 目标值（色相 / 明暗 / 彩度）
AmbientMotion（运动层：二阶色相 / attack-decay / 自适应起拍 / 空闲呼吸）
      ↓ 平滑后的状态（色相 / 明暗 / 彩度）
AmbientColorSpace（感知色空间：OKLCH → RGB，色域收敛压彩度）
      ↓ AmbientColor
AmbientLightService（**60 Hz 渲染时钟** + ΔE00 限速）
      ↓
AmbientLightWriter（原生：50 ms 节流 + 只写最新一帧）
```

三个时间尺度：

| | 频谱 | 颜色与运动 | 写入 |
| --- | --- | --- | --- |
| 旧版 | 10 Hz | 10 Hz | 10 Hz（100 ms） |
| **V2** | 10 Hz | **60 Hz**（独立渲染时钟） | **20 Hz**（50 ms） |

频谱还是 10 Hz（采集跑不快），但运动层在 60 Hz 上**逐帧积分**，所以曲线真的连续。

### 感知层：绝对 dB 不构成对比

母带压得响的歌所有频段都在 0.7 以上，录得轻的歌所有频段都在 0.2 以下。
所以**不能**直接拿绝对 dB 当亮度——那样灯永远是满的，或者永远不亮。

- **每段一个慢速参考电平**（τ = 2 s），相对值 = `(db − ref + 12) / 24`（±12 dB 映射到 0..1）。
  ⇒ 每段的**平均水平落在 0.5**，响的歌与轻的歌出来一样。
- **整体相对电平** = 按权重的**加权 RMS**（权重：前 4 段 3.0 / 4~11 段 1.6 / 其余 0.7）。
- **静音门**：峰值跟随 15 dB/s 回落，门限 −54 dB ± 6 dB。

> 静音门用 **−54 dB** 而不是演示台的 −70 dB：原生链路的 dB 被夹在 −54..0，
> 沿用 −70 会导致门永远关不上。

### 艺术层：三个信号故意不同步

| 输出 | 由什么驱动 | 时间尺度 |
| --- | --- | --- |
| 色相 | 频谱**质心**（音色） | 秒 |
| 明暗 | 整体相对电平 | 10~100 ms |
| 彩度 | 高频**瞬态**（镲片） | 10~50 ms |

三个信号来自频谱的不同统计量，**天然不同步** ⇒ 读起来是「流动」而不是「一起抖」。

- **质心**用频段**中心** `(i + 0.5) / N`（不是序号），所以是连续量，段一换不跳。
- **色相带 170°~320°**（青→蓝→紫→品红）：避开刺眼的亮黄，留 150° 行程。
- **明度区间映射**：`u = (x − 0.22) / 0.78`，`v = u^γ`，`γ = 1.45 + 0.5 × (1 − 灵敏度)`。
  典型电平落在**中间**而不是贴顶 —— 这正是旧版「明暗变化不明显」的根因。
- **彩度** = 0.10 + 饱和度 × 0.16 + 瞬态 × 0.05，上限 0.22。
- **感知明度** `L = 明暗 × 0.92 + 0.04`：暗部不是纯黑，顶部留 4 % 余量。

### 运动层：二阶色相

- **一阶系统只能限速，不能限加速**：大变化时灯会「甩过去」，中途换向还会顿一下。
  V2 把**角速度**也带进状态（`hueVel`），角加速度一起限 ⇒ 灯是**转过去**而不是被甩过去再停住。
- **亮度快起慢落**：attack 45 ms / decay 260 ms（非对称）。
- **自适应起拍**：阈值 = `max(0.12, 慢包络 × 1.25)`，外加**最短间隔 240 ms**
  （否则 120 BPM 的八分音符会每个都算一次起拍）。
- **空闲呼吸**：没声音时色相以 2.2°/s 缓慢漂移 + 底光按 6 s 周期呼吸，**不是冻在最后一个颜色**。

> **坑（第九十一轮修掉）：色相的速度公式少了一次「每帧 → 每秒」的换算。**
>
> ```
> // 错：share 是「这一帧收敛掉的比例」（无量纲），被当成了速度（度/秒）
> vDesired = delta * (1 - exp(-dt / tau))
> // 对：share 除以帧长（秒）才是速度
> vDesired = delta * share / (dt / 1000)
> ```
>
> 后果是色相以应有速度的 **1/64** 在爬：27° 的色相差要 **17 秒**。
> 灯于是**一直是同一个底色在变亮变暗** —— 明度那一路是另一个公式（正常），
> 所以只有亮度在动，看不出哪里不对。限速（60°/s）和限加速（240°/s²）这两道闸
> 在这条错误的速度下形同虚设，因为速度本来就远低于上限。
>
> 修的时候连带发现：空闲漂移会被跟踪器抵消（色相被拉回最后一个目标），
> 所以 `silent` 时不再追目标，只做漂移 —— 否则「不是冻在最后一个颜色」这条也废了。
>
> 为什么一直没被发现：单测都从默认状态起步，而**第一帧直接落在目标上**，
> 误差永远是 0，跟踪能力压根没被测到。要测它必须让色相**从别处出发**去追目标
> （见 `test/ambient_motion_test.dart` 的「the hue catches up with a target it did not start on」）。

### 五彩：四件套

默认的色相带是 170°~320°（150° 行程），而真实音乐的谱质心只在 **0.3~0.6** 之间移动——
直接乘进 150° 带里，色相实际只走 **100° 出头**。所以「五彩」不是一条滑杆，是四件套：

| 旋钮 | 键 | 范围 | 默认 | 解决什么 |
| --- | --- | --- | --- | --- |
| 色相跨度 | `ambient_hue_span_deg` | 150~360° | 150 | 色相带有多宽。**只拉它、不展开质心，色相仍只走 100° 出头** |
| 质心窗口展开 | `ambient_centroid_low` / `ambient_centroid_span` | 0~70 / 10~100 | 0 / 100 | 把真实质心的 0.20~0.65 这段拉伸成 0~1，让 150° 真正跑满（无独立滑杆，随预设生效） |
| 彩度上限 | `ambient_max_chroma` | 10~40（0.10~0.40） | 22（0.22） | 颜色最多能有多艳；硬上限 0.40 挡住色域外的请求 |
| 色相自转 | `ambient_hue_rotate` | 0~30 °/s | 0 | 频谱很窄、质心几乎不动时，让整条色相带自己慢慢转圈 |

三处公式（与 cardesk 逐行同构）：

```
u       = clamp((centroid − windowLow) / windowSpan, 0, 1)   // windowSpan 先夹 0.05..1
色相     = 320° − spanDeg × u                                 // spanDeg 夹 150..360
phase   = normalize(phase + speed × clamp(dt, 0..1 s))        // speed 夹 0..30 °/s
目标色相 = normalize(目标色相 + phase)                          // 仅 V2、非固定色、speed > 0
```

- **默认值必须与改造前逐位一致**：窗口 `(0, 1)` 是恒等映射，跨度 150 就是原来的色相带，
  自转 0 ⇒ 相位恒为 0，彩度上限 0.22 就是原来的 `MAX_CHROMA`。不传新参数时输出一个字节都不变。
- **自转相位在开灯、切换引擎时归零**；固定色模式不转（固定色转了就不叫固定色）。
- **彩虹预设**一次把四个旋钮配好，数值与 cardesk 的 `RAINBOW` 完全相同：

| 参数 | 值 | 参数 | 值 |
| --- | --- | --- | --- |
| attack | 40 ms | 色相跨度 | 360° |
| decay | 240 ms | 质心窗口低点 | 0.20 |
| 色相平滑 τ | 240 ms | 质心窗口宽度 | 0.45 |
| 色相限速 | 90 °/s | 色相自转 | 18 °/s |
| 色相限加速 | 360 °/s² | 彩度上限 | 0.32 |
| 每帧色差上限 | 2.2 ΔE00 | 基础亮度 | 12 % |
| 空闲呼吸 | 8 % | 饱和度上限 | 100 % |

#### 注意事项

1. **亮黄刺眼**：360° 跨度会把 60°~90° 的亮黄和纯红也放进来，夜间特别扎眼。
   所以彩虹预设同时把彩度压在 0.32、把「每帧色差上限」压到 2.2；
   如果仍然刺眼，把跨度收回到 300°~330°，或把彩度上限降到 0.26~0.28。
2. **红绿灯珠亮度不均**：门板 / 脚部的灯珠批次与亮度并不一致，高彩度 + 宽色相会把
   这种不均放大（同一颜色在不同分区看起来一深一浅）。验收时要在**夜间、低亮度**下看，
   而不是白天或最高亮度；必要时用「分区巡游」减少同屏对比。
3. **彩度要真的落到灯上**：运动层返回状态时夹的是**硬上限 0.40**，不再是 0.22
   （`ambient_motion.dart` 与 cardesk `AmbientMotion.kt` 同步改成 `maxChromaHard`）。
   0.22 只是**艺术层的默认值**：不选彩虹时 `chromaTarget` 仍按 0.22 输出，输出与改动前逐位一致；
   选了彩虹才把目标抬到 0.32 并原样送到灯珠。两边必须一起改，否则观感对不上。

### 跳跃：跳变

「跳跃」要的不是**更快地滑过去**，而是**直接换一个颜色**。

#### 为什么「把平滑调快」做不到跳变

色相链路是连续系统：每帧输出 = 上一帧 + 速度 × dt，而速度又受时间常数 τ、
限速、限加速约束。把 τ 从 240 ms 调到 60 ms、限速从 90 提到 180、限加速提到 800，
得到的只是**更短的滑动** —— 那一小段仍然是中间色，看起来是「唰」地甩过去，
而不是「啪」地跳到下一档；再快就会退化成每帧乱跳，方向也不受控。

跳变需要的是**量化**，不是更快的积分：把目标色相当场吸到最近的一档，
并且**清掉角速度**，否则下一帧的积分仍会把它从档位上拖走。

#### 做法（与 cardesk `AmbientMotion.kt` 同构）

```
step    = clamp(hueJumpDeg, 1°, 180°)
hue     = normalize(round(hueTarget / step) × step)   // 四舍五入到最近档
hueVel  = 0
```

- 只有 `hueJumpDeg > 0` 才走这条分支；`= 0` 时**原封不动**走原来的二阶跟踪
  （首帧落位、最短路径、限速、限加速都留在 `else` 里），默认观感逐位不变。
- 四舍五入的**半值方向**必须和 Kotlin 的 `Math.round` 一致（向正无穷），
  否则 30°、90° 这些正中间的色相会跳到不同档位。
- 120° = 三段：每跳一次跨 1/3 个色环，是「一眼看出换了颜色」又不会碎成闪烁的
  步长；60° 六档也可以选，但那更像是「换了个邻居」，不够刺激。
- 档位不是滑杆的「步进」：滑杆只决定档位大小，色相本身从不落在两档之间。

#### 每个起拍再前进一档

只吸档位还不够「跳跃」：色相跟着谱质心走，而真实音乐里质心只慢慢挪，
**几十秒才换一次色**。所以跳变模式下再加一条：**每来一次起拍就前进一档**
（拍间隔由「起拍间隔」管，默认 240 ms，跳跃预设 120 ms），鼓点一响就换色。

实现上有个坑：色相**每一帧都从目标重算**（`snapHue(hueTarget, step)`），
所以把「+一档」直接写进 `hue` 下一帧就被覆盖回去了。偏移必须单独记在
`AmbientMotionState.beatHueOffsetDeg` 里，随状态一帧帧带下去：

```
if (beat) offset = normalize(offset + step)
hue = normalize(snapHue(hueTarget, step) + offset)
```

连续模式（`hueJumpDeg = 0`）该偏移恒为 0，旧观感不受影响。

#### 换色间隔：没鼓点也要一直闪

起拍检测是**内容驱动**的：音乐没有鼓点、或者低音一直很响被自适应阈值当成
「常态」，就判不出起拍 —— 灯又定在一个颜色上。实测（两块桌面同时写同一个车控
通道时拍的那段视频）里，灯是**每 0.4~0.9 秒蹦一次**、每次跨 30~110°，
没有一次是几十秒不动的。

所以跳变模式再加一条上限：**隔 `jumpHoldMs` 至少换一档**（跳跃预设 380 ms）。

```
hop  = beat || (jumpHoldMs > 0 && now - lastHopAt >= jumpHoldMs)
```

`jumpHoldMs = 0` 仍是「只跟拍子」。两个条件互相兜底：有鼓点就跟着鼓点，
没鼓点也不会定住。

#### 跳跃模式下两层 ΔE 限速都关掉

这是「还是太平顺」的第二个来源：ΔE00 限速器存在的意义就是把跳变抹成滑动。
一次 120° 的换色 ≈ 20~30 ΔE，按每帧 6.0 的预算要拉十几帧 —— 到了车上就是一段
100~200 ms 的渐变，看起来仍然是「滑过去」。

所以 `hueJumpDeg > 0` 时：渲染层不走 `_limitDeltaE`，写入层也本来就是纯通道
（uni 没有写入层限速；cardesk 那边同时关 `setDeltaELimitEnabled`）。换色在
1~2 个写入周期（50~100 ms）内直接到位，和视频里 1~2 帧的跳变一致。

#### 起拍闪光与起拍间隔

原来写死的两个常量现在可调：

| 参数 | 键 | 范围 | 默认 | 含义 |
| --- | --- | --- | --- | --- |
| 色相跳变 | `ambient_hue_jump_deg` | 0~180° | 0（连续） | 0 = 平滑；>0 = 按该档位瞬间换色 |
| 起拍闪光 | `ambient_pulse_gain` | 0~200（0~2.00×） | 35（0.35×） | 一次起拍把亮度顶多抬多少 |
| 起拍间隔 | `ambient_beat_gap_ms` | 80~600 ms | 240 | 两次起拍闪光之间至少隔多久 |
| 换色间隔 | `ambient_jump_hold_ms` | 0 或 80~1000 ms | 0（只跟拍子） | 跳变模式下没鼓点也强制换色的上限 |

默认值 0 / 35 / 240 就是改造前写死的值（0.35×、240 ms），所以**不选跳跃时，
所有旧预设与旧观感的输出逐位一致**。

### 输出层：ΔE00 限速，以及这一轮修掉的**发散**

限速器把候选色拉回到与「上一帧」相差 ≤ 上限（OKLab 插值，不会穿过灰轴）。

> **只限渲染层不够**：被丢掉的那几帧的变化会攒到下一次写入，
> 真正落在车上的两帧色差可能好几倍。
> **只限写入层也不够**：候选色跑得比写入快，写入层每次都往回拉 ⇒ **误差每帧累积**，
> 几秒之后车上的颜色和音乐已经完全不是一回事了。

修法是**把预算按写入周期分摊**：

```
每渲染帧的预算 = 总预算 × 渲染间隔 / 写入间隔
               = 1.8 × 16 / 50
               = 0.576   (ΔE00)
```

| | 每 50 ms 能走多远 |
| --- | --- |
| 渲染层（3 帧 × 0.576） | 1.73 ≤ 总预算 1.8 |
| 写入层（1 次 × 总预算） | 1.8（**安全网**，正常不触发） |

于是渲染层**永远跑不过**写入层，写入层退化成安全网，**没有发散**。

> 限速器内部还留了一半余量（实际每帧只走预算的一半），
> 所以落到车上的相邻两帧 ΔE00 ≈ 0.9，远低于验收线 2.0。

**冷启动是「柔和渐亮」**：第一帧从近黑开始，按上面的速率爬到目标色（约 1~2 秒）——
这是刻意的，不是 bug。

#### 实测复核：写入层会不会把颜色越拉越远

有人怀疑过一个更严重的机制：

> 写入层以「上一个**已写**颜色」为基准、渲染层以「上一个**渲染帧**」为基准，
> 两层用**同一个**预算 ⇒ 候选色跑得比写入快一倍 ⇒ 写入层每次往回拉 ⇒
> 误差每帧累积 ⇒ 几秒后车上的颜色与音乐完全无关。

**当前代码里这个机制不成立**，两端的实际结构是：

| | uni（`AmbientLightWriter`） | cardesk（`AdaptapiAmbientLightApi`） |
| --- | --- | --- |
| 渲染层 | 基准 = 上一**渲染帧**（60 Hz），预算 = `1.8 × 16/50 = 0.576` | 同 |
| 写入层 | **根本没有 ΔE 限速**：只做 50 ms 节流 + 「颜色变化 < 2 个 RGB 单位就不写」的死区，**颜色一个字节都不改** | 基准 = 上一**已写**颜色（20 Hz），预算 = 完整的 1.8 |

所以 uni 这一侧连「往回拉」这个动作都不存在；cardesk 那一侧因为渲染预算已经按
`16/50` 分摊，渲染层一个写入周期内最多走 1.73 ≤ 1.8，写入层是**安全网**。

**实测（10 秒，两端各自的真实类）**：

| 量 | uni | cardesk |
| --- | --- | --- |
| 引擎原始步长（限速之前） | 中位 **0.88** ΔE/帧，峰值 12.2 | 中位 **1.00** ΔE/帧，峰值 12.5 |
| 渲染层限速之后 | 最大 **0.708**（上限 0.576） | 最大 **0.67** |
| 写入层触发拉回的次数 | —（无此机制） | 8 次 / 145 次写入 |
| **写下去的颜色 vs 渲染色** | 0（原生是纯通道） | **最大 0.0 ΔE** |
| 写入层造成的偏差随时间 | — | 前 1/3 段 0.0 → 后 1/3 段 **0.0**（不增长） |
| 渲染限速造成的滞后（限速**本身**的效果） | — | 28.6 / 32.6 / 29.8 ΔE（三个 1/3 段，**稳定**） |

⇒ **没有发散**：写入层从未改变过颜色；渲染层那个 30 ΔE 左右的「滞后」是
限速本身的效果（引擎想走得比预算快，限速器把它压住），它跟着音乐的动态范围起伏，
**不会一轮一轮地累积**。

> 顺带查清了一个更细的量：渲染层有 16/600 帧越过了 0.576 的上限。
> 原因是**8 bit 网格比预算还粗**——在这些暗蓝上，一个 RGB 步长本身就值
> 0.63 ΔE（`0,86,98 → 0,87,98` 就已经 0.632 ΔE），限速器在 OKLab 里插值完
> 再取整，取整后自然越界。**这是量化误差，不是发散**，而且它是写入层安全网
> 偶尔会响一下的唯一原因。

回归测试：`app/test/ambient_write_pipeline_test.dart`（uni）、
`cardesk/app/src/test/.../AmbientWritePipelineTest.kt`（cardesk）——
两个测试都直接断言「写入层造成的偏差**不随时间变大**」。

#### 「一直是一个底色」到底是怎么回事

30 秒的一次真实运行（`shots/13-ambient-colour-trajectory.png`）：

| 量 | 值 |
| --- | --- |
| 颜色走过的总路径 | **634 ΔE** ≈ 6.3 个色域宽度（一个色域宽约 100 ΔE） |
| 离第一帧最远 | **34.5 ΔE**（末帧仍在 25.5 ΔE 处） |
| 相邻帧色差 | 中位 2.17，最大 5.24 ΔE |

**颜色并没有卡住**——它一直在色域里走。看起来像「一个底色」有两个原因：

1. **它一直待在同一个色相楔里**：V2 的色相带是 170°~320°（刻意避开刺眼的黄），
   默认又是「跟随低频」模式（只看最低 8 段），实测色相目标被钉在 **235°~285°**
   这一楔子里。12 个色块并排放出来，全是暗蓝/蓝青，眼睛自然读成「同一个颜色」。
2. **动得最明显的是亮度**：亮度读数在 28~66 之间来回（起拍打亮、衰减变暗），
   颜色只是在这条明暗轴上小幅移动。

想让颜色家族宽一点：**切「跟随频谱」模式**（色相目标 224°~284°）、
或把**饱和度**调高（彩度上限 0.22）。这两项都在设置页里。

### 限速只对 V2 生效

旧版是**实车验证过**的观感（10 Hz 硬跳变）。限速是 V2 才有的东西，
套到旧版上会把它压成一条几乎不动的慢坡 ⇒ **「旧版 vs 新版」的 A/B 失去意义**。

所以设置页有**引擎切换**（新版 / 旧版 / 节奏），切到旧版时两层限速都关掉，
旧版链路**逐字保留**（`ambient_motion_legacy.dart` + 旧版调色板函数）。

### 节奏引擎（合并自上游 7c548f8）

上游 `feat/lynkco-05` 在 `7c548f8` 里独立做了一套「节奏检测 + 取色器」，
与本地的 V2 是两套实现，合并时**两边都保留**：上游那套成为第三个引擎
`engine = 节奏（峰值冲击）`（`AmbientLightSettings.engineRhythm = 2`）。

- 检测：`AmbientRhythm` 从 24 段里取低/中/高三区能量，用能量通量 + 区域阈值判起拍，
  并用最近若干拍的中位间隔估 BPM 与下一拍时刻（`nextBeatMs`），提前量 `beatLeadMs`（默认 140 ms）。
- 配色：三个区各一个色相（`bassHue` 12 / `midHue` 122 / `trebleHue` 252）与可选自定义色
  （`bassCustom/midCustom/trebleCustom`，空串表示用色相），按区能量做圆周加权得到色相。
- 输出：**峰值**（起拍）写颜色 + 车机亮度（`72 + impact × 28`，clamp 72~100），
  **谷值**在 `intervalMs × 0.22`（clamp 100~230 ms）后把亮度写到 `× 0.38`（仅车机亮度 > 50 时）；
  没有 BPM 时退化成 200 ms 一次的 5 Hz 流动（`pow(brightness, 1.28)`）。
- 兜底：开灯时先写一次静态色；采集没信号超过 1.5 s 时每秒重写一次静态色，灯不会黑。
- 这条链路**不做**两层 ΔE 限速（它就是靠「峰值/谷值硬写」出冲击感），
  但写入节流仍是 50 ms（20 Hz）。

> 合并时的两个取舍：默认颜色模式**保持「跟随低频」**（没有采用上游的
> 「默认跟随频谱 + 旧负载迁移」）；默认引擎仍是**新版**。换句话说，行为不因合并改变。

### 预设

十七个参数每个都有合理范围，但让用户在车里拖十五条滑杆不现实 ⇒ 六个预设：

| 预设 | 场景 | 换来什么 |
| --- | --- | --- |
| 均衡 | 日常 | 方案文档里的默认值 |
| 夜驾柔和 | 夜间、低速 | 更慢更弱、色差上限更紧、底光更低 |
| 赛博高对比 | 展示、性能车 | 快、对比强、彩度高 |
| 呼吸感 | 驻车怠速 | 慢、软，接近一次呼吸 |
| 彩虹 | 展示、想要五彩 | 跨度 360° + 质心窗口 0.20~0.65 + 彩度 0.32 + 18°/s 自转 |
| 跳跃 | 驻车展示、想跳色 | 色相 120° 瞬间跳变 + 每拍前进一档 + 换色间隔 380 ms + 起拍闪光 1.20×，底光 0，ΔE 限速关闭 |

预设**只改观感参数**，不动引擎、颜色模式、车机亮度、分区编排——
切预设不该把用户的选择一起抹掉。参数一旦被手动改过，预设行会诚实地显示「自定义」。

### 分区编排

这台车机**只有分区开关，没有分区颜色、没有分区亮度**（`0x2A` 段在本固件上没实现，
`set` 恒 false）⇒ 分区切换必然是**硬边**：一片亮、一片黑。

三条规则让它读起来像「呼吸」而不是「闪」：

1. **驻留约束**：每区至少 800 ms（可调 700~2000），慢于音乐的 1~2 Hz 律动；
2. **亮度补偿**：只亮一个分区时把全局 RGB 抬 ×1.6（补满要 ×3，会过曝）；
3. **顺序**：**先开新的、再关旧的** ⇒ 中间态是多一片亮着，而不是少一片。

**行车默认关闭**：分区轮流点亮在行车时是干扰。

| 最低亮度 / 最高亮度 | ❌ | ✅ | ✅ | 旧版的线性映射区间；新版用「基础亮度 + 感知明度区间」，**不读这两个值**；节奏拿它们当兜底色/谷值的区间 |
| 三区色相 / 自定义色 / 节拍提前量 | ❌ | ❌ | ✅ | 只有节奏引擎读（`engine == 节奏` 时显示） |
| 15 条 V2 参数（attack / decay / τ / 限速 / 限加速 / 色差 / 基础亮度 / 饱和度 / 色相跨度 / 色相自转 / 彩度上限 / 色相跳变 / 起拍闪光 / 起拍间隔 / 呼吸） | ✅ | ❌ | ❌ | 旧版/节奏是现网链路，没有这些参数 |
| 区域巡游 / 分区驻留 | ✅ | ✅ | ✅ | 分区编排与引擎无关 |

> 「拖了没反应」的滑杆比没有滑杆更糟 —— 所以旧版的亮度上下限在 V2 下直接**不显示**，
> 而不是摆在那儿让人以为坏了。

### 与 cardesk 的**有意偏差**

| | cardesk | 本实现 | 为什么 |
| --- | --- | --- | --- |
| 限速层数 | 渲染层 + 写入层（API 内） | **只有渲染层** | 本工程的原生侧是**纯通道**，写入层限速若放 Dart 会用「已发送」而不是「已写入」当基准 ⇒ 反而发散。预算全放在渲染层（按写入周期分摊），落到车上的相邻两帧照样达标。 |
| 限速归属 | 渲染层在控制器、写入层在 API | 全部在 Dart | 避免在 Java 里再实现一遍 CIEDE2000。 |
| 冷启动 | 柔和渐亮 | 柔和渐亮 | 一致。 |

### 上车验收清单

1. 引擎切到**新版**：灯应当**流动**，颜色在青→蓝→紫→品红之间缓慢移动，而不是一帧一跳。
2. 音乐停下时：灯**慢慢暗下去**并保留底光呼吸，**不冻在**最后一个颜色。
3. 鼓点：明暗有明显的起落，但**不闪**。
4. 引擎切到**旧版**：灯应当回到「一跳一跳」的现网观感（用来确认 A/B 有效）。
5. 「每帧色差上限」拖到 0.5：颜色移动应当明显变慢（说明限速真的在起作用）。
6. 「区域巡游」打开（**建议驻车时**）：三个分区应当轮流亮起，切换处**没有黑场**（先开后关）。
7. 亮度 `0` 仍然是**关灯**，不是最低档。

### 在模拟器上怎么看到「颜色和亮度真的在变」

车机上的频谱抓不到普通 app 的全局混音（Android 10 起需要 `CAPTURE_AUDIO_OUTPUT`），
所以模拟器上**放不出真实音乐**。但「颜色和亮度跟着音乐变」这件事**可以证明**：

```sh
cd uni-launcher/app
./tools/ambient_live_run.sh emulator-5554
```

这个脚本做两件事：**跑集成测试**，同时**并行抓模拟器物理屏**（两条独立通道互相印证）。

集成测试把**真实的设置面板**放在屏幕上（`AmbientLightSettingsPanel`，
含那个实时色块和「当前颜色 #xxxxxx · 明暗 NN」那行字），然后注入**合成的音乐频谱**
（底鼓在最低三段、旋律在中低段来回走、镲片在高段）：

- 频谱源被换掉，**其余全是生产链路**：感知层 → 调色板 → 二阶运动层 → ΔE00 限速 → 平台通道。
- 每 100 ms 一帧（10 Hz），跑 30 秒。
- 报告（`verification/ambient-live/emulator-report.json`）里带**整条颜色序列**：
  每一时刻的 hex 和明暗，外加**渲染像素**序列（见下）。

#### 像素级证据：量的是「画出来的像素」，不是引擎的自述

报告里除了引擎序列，还有一组 `pixels`：每 120 ms 一次，从 **RepaintBoundary 的图层树**
里读出**真正渲染出来的像素**——色块中心的 RGB，和亮度条的填充宽度。

这一层是刻意的：引擎说自己算出了什么，和玻璃上真的画出了什么，是两件事。
现在两者被逐帧对齐，并且断言**像素色必须等于引擎色**。

实测（`emulator-5554`，Android 10 / API 29）：

| 项 | 结果 |
| --- | --- |
| 引擎序列 | 300 帧，**272 个不同颜色**，明暗 24..65 |
| 渲染像素 | 40 个采样，**40 个颜色全不相同**，亮度 137..266 |
| 像素 == 引擎色 | **40 / 40 帧完全相等**（如 `#004c79` ↔ `#004c79`） |
| 亮度条填充宽度 | **530 .. 1249 px**（条宽 1893 px） |
| 亮度 ↔ 填充宽度 | 相关系数 **1.0** |

相关系数 1.0 说明：屏幕上的亮度条宽度，就是引擎亮度按比例画出来的宽度——
**亮度是真的在动，而且动在像素上**。

#### 两条互相印证的通道

上面的 `pixels` 是**第一条通道**：从 app 内部的图层树读出的渲染像素。
`tools/ambient_live_run.sh` 还会并行抓**模拟器物理屏**（`adb exec-out screencap`），
由 `tool/sample_ambient_screen.py` 从画面上量色块与亮度条——这是**第二条通道**，
完全在 app 之外（走的是模拟器的帧缓冲）。

实测同一轮（`emulator-5554`）：

| 通道 | 采样 | 不同颜色 | 亮度条填充宽度 |
| --- | --- | --- | --- |
| app 内图层树 | 40 帧 | 40（**全部互不相同**） | 568 .. 1230 px |
| 模拟器物理屏 | 279 帧 | **240** | 190 .. 1918 px |

**两条通道在同一时刻给出同一个颜色、同一个亮度**，误差 0~2 px：

| 物理屏量到 | app 内量到 | 亮度条（屏） | 亮度条（app） |
| --- | --- | --- | --- |
| `#004876` | `#004876` | 1231 px | 1230 px |
| `#003653` | `#003653` | 587 px | 587 px |
| `#004055` | `#004055` | 1174 px | 1174 px |
| `#005283` | `#005283` | 796 px | 794 px |
| `#004697` | `#004697` | 758 px | 756 px |

这就是「颜色和亮度真的在变」的完整证据：**引擎算了什么，屏幕上就是什么**。

`verification/ambient-live/` 下的产物：

- `emulator-report.json`：引擎序列 + 渲染像素序列；
- `evidence.json`：两条通道的原始测量；
- `swatch-strip.png`：12 帧实测画面的拼图，肉眼直接看得出颜色和亮度条在动。

#### 踩过的坑：`convertFlutterSurfaceToImage()` 会把物理屏冻住

Android 上 `binding.takeScreenshot()` 必须先调 `convertFlutterSurfaceToImage()`，
而这个调用会把 Flutter 的渲染面**换成离屏 ImageReader**——**模拟器屏幕从此不再刷新**。

症状极具迷惑性：`screencap` 连拍十几帧，**每帧字节完全相同**（同一个 md5），
看起来像「颜色根本没变」；而 logcat 里的引擎日志却明明在刷几百个不同 hex。
真相是：**引擎在跑，屏幕被冻住了**。连 `input tap` 都不再有任何反应。

两个坑连在一起：

1. 第一次跑 `flutter drive` 时构建失败（`UNI_SIGNING_STORE` 没设，keystore 在
   `app/android/uni-debug.keystore`）——先补上这个环境变量。
2. 之前那批「16 张一模一样的截图」全部作废：不是颜色没变，是屏幕被冻住了。
   重装应用（`am force-stop` + 重新启动）即可解冻。

所以现在**不走截图通道**：像素直接从图层树读（`RenderRepaintBoundary.toImage()`），
物理屏则由 `tool/sample_ambient_screen.py` 在测试运行期间并行抓取。

> **这一步抓到过什么**：第九十一轮修色相速度公式之前，
> 目标色相在 216°~270° 之间摆，**实际输出的色相却卡在 244.3°~244.6°**
> （只动 0.3°）—— 那就是「一直是同一个底色」。

## 车机待验证

1. **功能号能否按名解析**：装机后看 `dumpsys activity xyz.i4o.uni.launcher/.MainActivity --uni-state` 里 `ambientLight.unresolved`，列出解析不到的名字。
2. **写值是否被车机接受**：观察日志 `UniAmbient`（`氛围灯开关已下发` / `氛围灯颜色已下发`）与车机是否有实际灯光变化。写成功但灯不动，说明写入通道与灯光不是同一条路径。
3. **三个分区是否都亮**：只写主区时上/下分区不亮，是厂商设计；确认实车三个分区是否都有灯珠。
4. **亮度 0 是否等于关灯**：确认与仪表/原车设置一致。
5. **静止亮度是否需要单独写**：当前两套都写；若实车表现异常，先回退成只写行车那一套。
6. **音乐律动模式是否由车机自己做**：厂商的「互动效果」本身可能有内置灯效；确认我们写自定义色后，灯效来源到底是自定义色还是车机自带。
